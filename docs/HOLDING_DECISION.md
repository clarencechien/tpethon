# E13：有上限的轉乘等候與收斂判斷

[互動頁](https://clarencechien.github.io/tpethon/holding.html) · [E12候選來源](SERVICE_SEARCH.md) · [E11資料](RAIL_HUB_TRIAL.md)

**決策：暫不推薦直接開行這份四車班表；先補最小實測資料，停止此支線的自動調參。** 這不是證明接駁、hub或BRT一般都無效，而是本輪的固定候選與四種等候規則未取得足以支持試辦的穩定結果。

## 固定什麼，測什麼

沿用E12在240人、列車間隔10分鐘、50%省時目標下選出的候選：4輛營運車＋1輛備車、5分鐘首班銜接緩衝。原方式仍是2輛＋1備車；BRT比較條件固定4輛＋1備車、2分鐘緩衝。沒有重選車隊、加快速度、改旅客期限或加入新轉乘者。

只測最多等0／2／4／6分鐘。兩種資訊條件為固定預估步行6／9分鐘；十個新種子401、503、607、709、811、907、1009、1103、1201、1301，與E12挑選及驗證種子分開。所有人仍來自同一合成分布，不能當成新實測證據。

|情境|列車晚到|額外步行|巴士去返程倍率|
|---|---:|---:|---:|
|無額外延誤|0|0|1|
|轉乘延誤|5分|3分|1|
|道路延誤|0|0|1.25|
|全部延誤|5分|3分|1.25|
|新壓力條件|8分|5分|1.4|

5種延誤 × 2種資訊 × 10種子＝100組，四規則共400筆結果。沒有用結果再挑最有利的種子或延誤條件。不等候不受步行預估影響，因此有重複結果；次數不是成功機率，也不是100份獨立資料。

## 等候控制器可知道的事

模型在可發車時間 `now = max(計畫時間, 車輛可用時間, 上班發車+1分鐘)` 做一次判斷：

1. 只讀已發生的列車開門訊息 `doorTime <= now`，以及目前站牌已到人數。不讀未來實際旅客到站或未來車程。
2. 預估到站＝開門時間＋固定預估步行時間。若在 `now` 之後、`now+等候上限` 之前，且不超過10時發車截止，才等到最近的這個預估時間。
3. 滿車不等；沒有合格訊息不等；預估到站超過上限時直接發車，不是等滿上限碰碰運氣。判斷後不延長、不依實際到站偷改等候時間。
4. 先到的旅客先上車；等候期間到達者可使用剩餘座位。若最後仍無人，車輛也已占用至等候釋放時刻，再取消空班。
5. 真實車輛返回與12分鐘休息完成後才能再用；等候延後去返程、後續班次及必要的超時計費。

列車訊息假設即時可靠；未驗證現場是否可取得。固定6／9分鐘預估刻意與實際步行6／9／11分鐘比較；不是完美預測。沒有訊息中斷、個別步行差異、站位衝突、上客服務時間或從上游載來的直通乘客。所稱「車上等待」僅指本模型在松山hub先上車的旅客。

## 舊門檻的盲點與本輪更正

第一輪固定測試發現：在最嚴重情境，原兩車方式與四車候選都240人晚到，卻仍可能符合「沒有新增晚到」。**相對改善不代表可接受的絕對服務水準。**

因此保留相對門檻原始成績，再加95%準時的診斷門檻。這是看過稽核結果後新增的明示修正，並非事前登錄或外部標準；加入後沒有重選任何車數、緩衝、等候規則或驗證樣本。

- 相對門檻：每人至少省3分鐘、保留BRT條件至少一半省時、全部12時前完成、費用低於BRT條件；相對原兩車方式無新增晚到，且相對四車不等候也無新增晚到。
- 絕對門檻：準時人數／全部旅客至少95%。到達期限仍是假設每人出門後75分鐘，不是真實工作時刻。
- 本輪停止判斷：沒有任何一條固定規則在全部100組條件同時通過以上門檻，暫不將此候選推薦為可試辦服務。不把「最多通過幾次」改叫穩定方案。

|最多等候|通過相對門檻／100|再要求95%準時／100|相對不等候，最差新增晚到|
|---|---:|---:|---:|
|0分鐘|36|16|0人|
|2分鐘|36|16|21人|
|4分鐘|36|16|71人|
|6分鐘|38|18|71人|

新的最嚴重情境下，四種規則準時率皆0%。BRT比較條件也可能晚到，不能把它當成無限可靠的標準答案。此結論是固定假設的反例，不是實測內湖準時率。

## 逐人與逐車稽核

固定公開完整紀錄的例子：種子401，列車晚5分、步行多3分、巴士車程125%，預估步行9分鐘。

最多等4分鐘相對不等候：161人較早到、79人較晚到；其中44人由準時變晚到。62名先上車旅客累計等待191.4人分鐘。總晚到由154降至130，仍不能忽略新增受害的44人；有人恢復準時與有人新晚到可同時發生。

平均省時以相同ID配對，計入所有人；超過12時或未完成者以12時截尾另報未完成人數。早／晚／不變也採同一觀察上限。車上等候人分鐘已包含在全程變化，不再次相加。沒有把「準時但稍晚到」藏在零新增晚到的數字裡，另列所有較早與較晚者。

## 與E11、E12的可比性

E11模型檔與E12輸出保持不變。E13為讀取舊合成人群及班表函式的獨立派車重播；零等候、原兩車方式與BRT條件均經測試逐項對上E11的平均時間、費用、里程、未完成與新增晚到。

仍沿用E11候選OSRM小客車路徑，尚未核准公車行駛；真實VD快照及公車站序只提供現勘與服務背景，不把它們冒充完整車程／容量。既有[研究引用與原文頁碼](BRT_TRANSITION.md)用作背景；本輪等候規則是專案自訂模型，沒有宣稱來自已驗證的內湖論文。沒有新API請求。

成本仍是每車小時1,200元、至少3小時含備車、超時另計，BRT另假設12,000元設施分攤。沒有報價、道路壅塞回饋、專用道空間或其他用路人的代價；結果不能當工程投資評估或減塞百分比。

## 收斂後的最小下一步

暫停此班表支線的參數搜尋。建議先在松山站候選轉乘服務收集至少3個一般工作日07:00–09:30的匿名事件紀錄，包含至少一次延誤時段。這只是啟動校正的建議規模，不是統計充分性保證，也不代表全年。

|要回答的問題|需要記錄|用來修正什麼|
|旅客能否趕上接駁|列車開門、到站牌、巴士到離站、沒搭上人數|實際步行分布與班次銜接|
|車回得來嗎|同車去程、回程、休息與下一次發車|完整週期與有限車隊|
|是不是下游路口拖慢|時間對齊的轉向、號誌、排隊尾端|區分橋面與下游瓶頸|
|服務是否可用|真實到達期限、候車場地、可調度車隊與報價|絕對準時目標、場地與成本|

先用實際事件做不載客的班表重播，保留不同日期驗證，且不因結果不好而改門檻。若只能繼續用合成資料，可做敏感度研究，必須標成研究，不能宣稱已收斂為現實可行方案。

## 重跑

```sh
node scripts/run_holding.mjs
node --test tests/holding_logic.test.mjs
```

`data/simulation/holding-results.json` 保存400筆結果、資訊與延誤條件、完整固定案例及輸入／舊模型／新模型／執行器SHA256。不需網路、金鑰或新增套件。

測試包括不預知未來的手算、上限／滿車／發車截止、零等候與舊模型對照、乘客與車輛守恆、車上等待、配對受害者、全結果重算與全員晚到不能通過絕對門檻。瀏覽器測試 `python tests/holding_pages_smoke.py` 驗證條件切換、準時率、固定稽核案例、手機版與缺檔狀態。
