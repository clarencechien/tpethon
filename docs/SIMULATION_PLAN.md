截至 2026-10-16（臺北時間）。本次建立的可執行模型是**載客量與車隊需求試算**；尚未校正能預測內湖限行成效的路網模型。情境設定見 [scenarios.json](../simulation/scenarios.json)。

## 二、兩週如何比較

週摘要保留每一天、上午07:00–09:30、下午17:00–19:30、離峰10:00–16:00及每15分鐘時間格。計算有效方向觀測中低速（<20 km/h）與低速且占有率≥25%的占比；先等權平均當日快照，再等權平均日期。缺格不插補，速度不是路段旅行時間。

原始週摘要包含週末，不能直接把完整上週與部分本週平均相減。配對比較只保留兩週同星期、同整點時間與雙方都有效的VD×LinkID，每組日期須有至少80%時間格可配對。日曆參考標為休假者不納入配對；[參考鏡像](https://github.com/ruyut/TaiwanCalendar)的10/9為補假，尚待官方行事曆核對，亦不代表企業實際出勤。

候選走廊只採週一至週五且參考日曆未標休假者，需至少三個有效日期、每個日期至少80%時間格有有效樣本，依低速且高占有率占比排序。這只用於人工查看測站、路口紅燈、故障與排隊外溢，不證明瓶頸原因。

### 本批實際結果與第一批查證位置

截至10/16，已取得上週7天、本週10/12–10/15共4天。兩份週摘要加索引為717,707 bytes，新增道路／公車參考輸入為265,642 bytes；原始大檔未提交Git。

配對四組週一至週四日期後：晨尖峰40個配對時間格，低速觀測占比由7.94%到7.56%；晚尖峰39格，由10.96%到9.59%。這些只是本批共同有效感測器的觀測差異，不能推論改善成因，亦不是通勤延誤比例。

兩週晨尖峰均列入優先查證的候選為**陽光街東向、新明路東北向**。本週低速且高占有率的平均占比分別約71.1%、60.3%，各有4個合格日期。下一步先核對對應VD、路口紅燈、設備狀態及上下游排隊，再決定能否作模擬校正點；不因排名就直接選為封路區域。

## 三、目前可以執行的模型 M0：接駁容量

[Plan 頁面](https://clarencechien.github.io/tpethon/plan.html)可調整私車乘員人次、改搭巴士比例、容量、載客率、尖峰長度、循環時間、乘員率及備車比例。人次預設10000只是示例，不由 VD 或捷運數字推定。

1. 轉乘人次 = ceil(假設私車人次 × 轉乘比例)。
2. 每班有效容量 = floor(額定容量 × 規劃載客率)。
3. 所需最少發車班次 = ceil(人次 / 有效容量)。
4. 每小時班次 = ceil(最少班次 / 尖峰小時數)。
5. 營運車輛 = ceil(每小時班次 × 循環分鐘 / 60)，備車另外向上取整。

顯示60分鐘、使用者設定、120分鐘的循環時間敏感度。這是均勻班次與需求的容量帳，不包含路線分配、站台排隊、空駛、車輛上線／下線與駕駛工時。更短的循環時間不是預測結果；需實測或另模擬公車優先才可採用。

## 四、M1：現況路網校正，先過關再談封路

**建議演算法：SUMO 微觀模擬＋迭代動態交通指派（DTA）。** 已核對 [SUMO 官方 DTA 文件](https://sumo.dlr.de/docs/Demand/Dynamic_User_Assignment.html)中的 `duaIterate` 工作流程；本次尚未執行 SUMO 路網模擬。 取得需求範圍後以有約束的OD估計為初值，反覆路徑選擇、模擬及感測器比對。VD不足以唯一識別OD，要保留多組合理OD及轉乘／改道假設。

必要準備：

- 擴大到內湖外圍替代路徑、橋樑與國道匝道；路網必須有轉向限制、路口連接、高架層級、車道、速限及號誌相位。不能只按幾何交叉連線。
- 明確定義進出研究區的斷面，人工核對每條車道和方向，只計一次；確認來源 Volume 的實際統計區間後才校正流量，不能用 UpdateInterval 直接推定。
- 對需求使用企業通勤調查／匿名聚合OD與乘員率，區分居民、穿越車流、物流、汽車與機車；保留必要通行。
- 公車需核對路線變體、班次、實測站間時間、上下車／乘載與滿載拒載；駕駛休息及折返設施另建約束。
- 用不同日期分校正與保留驗證組，按降雨、星期、假日、工程與事故分層。兩週是第一批資料，不足以代表全年季節。

檢查方向別車速、已確認區間的車流、公車旅行時間及可觀察的排隊位置／開始時間；同時報告缺測率。校正門檻須依量測誤差及用途訂定，不能只讓一個平均值接近。**未通過驗證，不輸出「限行會省幾分鐘」或「此路應封閉」。**

## 五、M2：四類政策情境

| 情境 | 參數 | 重點檢查 |
|---|---|---|
| 私車轉接駁 | 轉乘10/20/30%，多組乘員率與需求 | 是否真正取代汽機車旅次、滿載及等車 |
| 公車優先 | 號誌優先、專用道、站位 | 公車循環、一般車與路口延誤、行人影響 |
| 尖峰限行 | 明確邊界、時段、必要通行與穿越車流限制 | 外圍回堵、改道、未完成旅次；不得只看區內速度 |
| 錯峰上班 | 提前／延後30/60分鐘、參與10/20/30% | 保持總需求，檢查是否只是把壅塞移時 |

結果以人時、旅行時間P50/P95、公車等候／擁擠、排隊外溢、車公里、營運成本與必要通行可及性比較；至少報告需求、遵從率、下雨及循環時間敏感度。Braess悖論只是可能機制，不當成內湖限行必定有效的前提。

## 六、可重現流程與儲存

```sh
python scripts/backfill_weeks.py --as-of 2026-10-16
python scripts/summarize_weeks.py --as-of 2026-10-16 --calendar local-data/simulation/calendar-2026.json
python scripts/fetch_simulation.py

```

行事曆快取需從上述公開鏡像下載；省略 `--calendar` 則標成未知，不把未知當成官方工作日。TDX使用現有`tdxid`/`tdxsec`；腳本不輸出金鑰，逐日下載、沿用快取，遇到429採有限退避。

**本次 GitHub 新增的是兩週摘要和小型參考輸入。** 原始全市下載與新增逐日回放檔只保留本機 `local-data/`；先前已提交的10/15回放保留。週摘要有日期與來源雜湊，GitHub Actions已設定每日台北時間11:23、23:23更新上週／本週摘要，需在Actions另設TDX secrets。歷史通常最多到昨天，下載不完整則保留上次成果；成功提交後自動部署Pages。完整原始資料逐日約百MB壓縮，未來長期累積應使用物件儲存與Parquet，不放進Git。
