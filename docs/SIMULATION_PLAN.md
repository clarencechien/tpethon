## 二、兩週如何比較

週摘要保留每一天、上午07:00–09:30、下午17:00–19:30、離峰10:00–16:00及每15分鐘時間格。計算有效方向觀測中低速（<20 km/h）與低速且占有率≥25%的占比；先等權平均當日快照，再等權平均日期。缺格不插補，速度不是路段旅行時間。

原始週摘要包含週末，不能直接把完整上週與部分本週平均相減。配對比較只保留兩週同星期、同整點時間與雙方都有效的VD×LinkID，每組日期須有至少80%時間格可配對。日曆參考標為休假者不納入配對；[參考鏡像](https://github.com/ruyut/TaiwanCalendar)的10/9為補假，尚待官方行事曆核對，亦不代表企業實際出勤。

候選走廊只採週一至週五且參考日曆未標休假者，需至少三個有效日期、每個日期至少80%時間格有有效樣本，依低速且高占有率占比排序。這只用於人工查看測站、路口紅燈、故障與排隊外溢，不證明瓶頸原因。

### 本批實際結果與第一批查證位置

截至10/16，已取得上週7天、本週10/12–10/15共4天。兩份週摘要加索引為717,707 bytes，新增道路／公車參考輸入為265,642 bytes；原始大檔未提交Git。

配對四組週一至週四日期後：晨尖峰40個配對時間格，低速觀測占比由7.94%到7.56%；晚尖峰39格，由10.96%到9.59%。這些只是本批共同有效感測器的觀測差異，不能推論改善成因，亦不是通勤延誤比例。

兩週晨尖峰均列入優先查證的候選為**陽光街東向、新明路東北向**。本週低速且高占有率的平均占比分別約71.1%、60.3%，各有4個合格日期。下一步先核對對應VD、路口紅燈、設備狀態及上下游排隊，再決定能否作模擬校正點；不因排名就直接選為封路區域。

## 三、目前可以執行的模型 M0：接駁容量

[Plan 頁面](https://clarencechien.github.io/tpethon/plan.html)可調整私車乘員人次、改搭巴士比例、容量、載客率、尖峰長度、循環時間、乘員率及備車比例。人次預設10000只是示例，不由 VD 或捷運數字推定。

1. 轉乘人次 = ceil(假設私車人次 × 轉乘比例)。
2. 每班有效容量 = floor(額定容量 × 規劃載客率)。
3. 所需最少發車班次 = ceil(人次 / 有效容量)。
4. 每小時班次 = ceil(最少班次 / 尖峰小時數)。
5. 營運車輛 = ceil(每小時班次 × 循環分鐘 / 60)，備車另外向上取整。

顯示60分鐘、使用者設定、120分鐘的循環時間敏感度。這是均勻班次與需求的容量帳，不包含路線分配、站台排隊、空駛、車輛上線／下線與駕駛工時。更短的循環時間不是預測結果；需實測或另模擬公車優先才可採用。

## 三之一、已執行的 M0b：雙通道排隊情境實驗

[互動模擬](https://clarencechien.github.io/tpethon/simulation.html)可調整需求、容量、轉乘、錯峰與改道比例；比較六個情境、逐分鐘排隊曲線、主要／外圍色塊及容量±20%敏感度。實測週摘要只作查證位置參考，沒有被當成需求或容量輸入。兩條通道是抽象的平行通道，**沒有對應到陽光街、新明路或任何具體街道**。

### 演算法與守恆

- 用確定性的流體點排隊模型，每分鐘更新一次；不是 SUMO、完整動態交通指派或 Braess 悖論實驗。需求為人工單峰：第 i 分鐘權重 `0.55 + 0.9 sin(π(i+0.5)/N)`，正規化後分配總人次。
- 每通道到達率 a、通過能力 c 皆以 PCU／分鐘表示。`Q(t+1)=max(0,Q(t)+a-c)`，離開量為 `Q(t)+a-Q(t+1)`。每分鐘內假設均勻到達，精確積分線性隊列面積；中途排空時以三角形積分，不高估到該分鐘末。
- 需求 = 私車乘員 + 改搭巴士人次；私車數 = 私車乘員／假設乘員率（允許流體小數）。限行只把原走主要通道的指定比例私車移往外圍，保持全部旅次；錯峰把剩餘私車指定比例延後30–120分鐘（介面也允許0、15分鐘），不在原尖峰截止時丟棄。
- 巴士依累積人次達有效載客量發車，最後一分鐘送出未滿一車的餘額。這是需求反應的理想化發車，不是固定班表。加入每輛巴士的道路占用 PCU，全部走主要通道；沒有路線分配、返程車流或既有公交供給。兩通道容量假定為扣除背景交通後可供本批旅次使用的容量。
- 營運車隊 = 任一固定循環時間窗口內最大發車數，備車另向上取整。循環時間由使用者輸入，不由排隊結果反饋；必須另作60／90／120分鐘等試算，不能保證車輛或駕駛排班可行。與 M0 均勻班次的算法不同，尖峰集中時通常需要更多車。
- 模擬包含延後旅次與尖峰後排空；最多算到基本觀測窗後720分鐘。若仍有隊列，回傳 residualPCU、時間總量標成下限，介面停止比較改善百分比。點排隊沒有儲車長度限制或上游回堵，不能換算排隊公尺。

### 指標與第一輪結果

排隊面積／60為「PCU·小時」，加上兩通道假設自由行駛時間後為道路當量時間總量。外圍較長的行駛成本有計入。這些指標不是乘客人時，**沒有納入巴士等候、上下車、乘客車內時間、物流影響與營運成本，不能據此宣告全改巴士就是最佳政策**。

示例：10,000人、每私車1.3人、07:00起150分鐘、70%原走主要通道；主要容量2000、外圍1400 PCU／時；自由行駛12分鐘、外圍額外8分鐘。巴士70人、載客率80%、每輛2.5 PCU、固定循環90分鐘、備車10%。三種政策各20%，錯峰延後60分鐘。以下皆為模型假設結果，四捨五入：

| 情境 | 私車旅次 | 巴士班次／含備車車隊 | 主要／外圍最高隊列 PCU | 排隊 PCU·時 | 含行駛 PCU·時 |
|---|---:|---:|---:|---:|---:|
| 參考 | 7692 | 0／0 | 808／0 | 1067 | 2913 |
| 20%改搭巴士 | 6154 | 36／29 | 181／0 | 155 | 1650 |
| 20%私車延後60分鐘 | 7692 | 0／0 | 505／0 | 564 | 2410 |
| 主要通道20%私車改道 | 7692 | 0／0 | 137／301 | 447 | 2437 |
| 三者合併 | 6154 | 36／29 | 0／0 | 0 | 1610 |
| 本批人次全改巴士 | 0 | 179／140 | 0／0 | 0 | 90 |

這組假設下，單純改道減輕主要通道，卻讓外圍出現最高301 PCU隊列。另以主要容量6000、外圍600測試全部改道，確認總排隊惡化；不是所有限行都有效。把全部私車一起延後60分鐘的測試，排隊總量不變，只把發生時間往後推。容量敏感度不是實測雨天情境或統計信賴區間。

可重現：[程式](../static/simulation_logic.js)、[本輪輸入與完整輸出](../data/simulation/experiment.json)。瀏覽器可下載自己的情境 JSON；不需要 TDX secrets。執行：

```sh

```

## 三之二、實測型態與年成長已接入

模型 v2 增加 `demandWeights`，可使用單一 VD×LinkID 的實測 Volume 相對分布取代人工單峰。兩週原始 compact 檔產生 [profiles.json](../data/weeks/profiles.json)，本批386組上午／下午型態，約415KB。每組只用參考日曆非假日的週一至週五，每日10個整刻樣本必須全部有效；至少3天，所有時槽使用相同日期集合。零流量保留，缺格／異常不補零；設備名稱、方向、位置或車道數改變者不跨日混用。不同測站與方向分開，並記錄逐日數值及來源檔 SHA-256。

已再次核對 [TDX歷史API官方OAS](https://tdx.transportdata.tw/webapi/File/Swagger/V3/4b4708cc-ab49-4037-a896-e24544d51609) 的 `Vehicle.Volume`，說明僅為「流量偵測值, -99=資料異常」，沒有明確統計區間。因此**不把10個樣本加成150分鐘車流、不乘15當成實際累積量、不反推出全區人次或容量**。介面的實測曲線保留原始來源區間單位；每個樣本權重固定延展15分鐘後正規化，是為排隊模型建立分布的假設，不是補出實測分鐘流量。來源包含混合車種；私車需求只是借用此相對分布。觀測通過量可能受瓶頸排隊壓低，亦不是潛在到達需求，需進一步校正。

複利：`基期值 × (1 + 年成長率)^年數`。介面可設定道路需求、道路容量、捷運既有旅次三個獨立年成長率，支持負成長，年數0–20。道路模型只將假設總人次與容量依設定成長，時段型態維持不變；不由兩週資料估計年成長率、不推估季節／天氣變化。每年從同一個基期重新計算，避免將成長後數值再當成基期；六情境、排隊回放與匯出皆使用所選目標年。

捷運另用既有2026-09實測：414439旅次／22個週一至週五 = 18838.13636人次。統計範圍是07–10進站且目的地為西湖／港墘，不是到站時間，也未排除國定假日。以假設2%成長5年為例，變成20798.82人次（+10.408%）；這是既有捷運需求的獨立情境，不加入道路開車人次、不假定列車有足夠剩餘容量。道路與捷運相對年數各從自己的基期出發，並不把不同日期當成同一天。

圖表包含實測樣本／目標年Volume情境、各年假設道路人次／捷運獨立人次，以及各年無政策／所選政策排隊。未排空年度不連線，表格標示時間總量下限。缺少或雜湊不符的實測檔會停止實測模式，不暗中改成人工或零需求；可明確選擇人工示例繼續。匯出 JSON 附基期、成長率、年份、測站、日期、型態樣本與檔案雜湊。

## 四、M1：現況路網校正，先過關再談封路

**建議演算法：SUMO 微觀模擬＋迭代動態交通指派（DTA）。** 已核對 [SUMO 官方 DTA 文件](https://sumo.dlr.de/docs/Demand/Dynamic_User_Assignment.html)中的 `duaIterate` 工作流程；本次尚未執行 SUMO 路網模擬。 取得需求範圍後以有約束的OD估計為初值，反覆路徑選擇、模擬及感測器比對。VD不足以唯一識別OD，要保留多組合理OD及轉乘／改道假設。

必要準備：

- 擴大到內湖外圍替代路徑、橋樑與國道匝道；路網必須有轉向限制、路口連接、高架層級、車道、速限及號誌相位。不能只按幾何交叉連線。
- 明確定義進出研究區的斷面，人工核對每條車道和方向，只計一次；確認來源 Volume 的實際統計區間後才校正流量，不能用 UpdateInterval 直接推定。
- 對需求使用企業通勤調查／匿名聚合OD與乘員率，區分居民、穿越車流、物流、汽車與機車；保留必要通行。
- 公車需核對路線變體、班次、實測站間時間、上下車／乘載與滿載拒載；駕駛休息及折返設施另建約束。
- 用不同日期分校正與保留驗證組，按降雨、星期、假日、工程與事故分層。兩週是第一批資料，不足以代表全年季節。

檢查方向別車速、已確認區間的車流、公車旅行時間及可觀察的排隊位置／開始時間；同時報告缺測率。校正門檻須依量測誤差及用途訂定，不能只讓一個平均值接近。**未通過驗證，不輸出「限行會省幾分鐘」或「此路應封閉」。**

## 五、M2：四類政策情境

| 情境 | 參數 | 重點檢查 |
|---|---|---|
| 私車轉接駁 | 轉乘10/20/30%，多組乘員率與需求 | 是否真正取代汽機車旅次、滿載及等車 |
| 公車優先 | 號誌優先、專用道、站位 | 公車循環、一般車與路口延誤、行人影響 |
| 尖峰限行 | 明確邊界、時段、必要通行與穿越車流限制 | 外圍回堵、改道、未完成旅次；不得只看區內速度 |
| 錯峰上班 | 提前／延後30/60分鐘、參與10/20/30% | 保持總需求，檢查是否只是把壅塞移時 |

結果以人時、旅行時間P50/P95、公車等候／擁擠、排隊外溢、車公里、營運成本與必要通行可及性比較；至少報告需求、遵從率、下雨及循環時間敏感度。Braess悖論只是可能機制，不當成內湖限行必定有效的前提。
