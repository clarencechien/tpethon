# 封一段路、改單行：從示範走向內湖實測

[互動示範](https://clarencechien.github.io/tpethon/network.html) · [資料、方法、引用](https://clarencechien.github.io/tpethon/methods.html)

## 目前完成到哪裡？

已完成四節點假想路網的互動教學，可切換中間連接道原方向、封閉或反向單行。使用固定每小時需求的靜態使用者均衡解析解；**沒有套上內湖道路，沒有完成 SUMO 校正，也沒有提出封路地點**。

這個例子解釋可能機制：每個人選自己最快的路，可能使大家集中在互相干擾的路段；限制一條路後重新分配，總體可能變好。但需求較少時，限制同一條路反而可能變慢。方向、需求與周邊替代路徑都會改變答案。

## 可重現的教學模型

起點 S、終點 T、中間節點 A 與 B。外圍四條有向邊為 S→A、A→T、S→B、B→T；中間連接道可 A→B、B→A，或封閉。

- S→A 與 B→T：分鐘數 = 該邊每小時車流 / 100。
- A→T 與 S→B：固定 45 分鐘。
- 中間連接道：0 分鐘。
- 每輛車都必須抵達；沒有刪除需求、號誌、空間排隊、隨機行為、運具轉換或公車。這些成本函數是本站自訂教學假設，不是道路容量量測值。

令 q 為每小時需求、u/l 為上／下路徑流量、z 為走中間連接道的路徑流量。

| 狀態 | 需求範圍 | 路徑分配 |
| --- | --- | --- |
| 封閉 | 全部 | u=l=q/2，z=0 |
| A→B | q≤4500 | u=l=0，z=q |
| A→B | 4500<q<9000 | u=l=q−4500，z=9000−q |
| A→B | q≥9000 | u=l=q/2，z=0 |
| B→A | q≤9000 | u=l=q/2，z=0 |
| B→A | q>9000 | u=l=4500，z=q−9000 |

將路徑流量加總到邊，再代入成本函數。使用中的路徑同時耗時相等、未使用的可達路徑不更快，符合「沒有人能單獨改道就更快」的使用者均衡。這不是社會最適流量，也不是動態交通指派。

4000 輛／小時時，原狀每車 80 分鐘，封閉後 65 分鐘；1000 輛時，原狀 20 分鐘，封閉後 50 分鐘。兩個方向的結果都公開，不能只展示有利結果。

[解析程式](../static/network_logic.js)及[測試](../tests/network_logic.test.mjs)驗證所有需求區段的旅次守恆、節點流量守恆、均衡條件、零需求與非法輸入。這些數字不是從論文擷取，也不是內湖旅行時間。

## 封路與單行的實驗矩陣

同一段道路的起訖、方向、時段與適用車種要寫清楚。先固定相同起訖需求與出發時間，再另測改時間／改運具的反應，避免把需求減少錯當成封路效果。

1. 原狀：當作所有比較的共同基準。
2. 尖峰禁止穿越私車：居民、送貨、救護與公車例外另列，不能視為完全封路。
3. 尖峰整段封閉：被影響的旅次重新找路；無法抵達的旅次獨立報告，不能刪掉。
4. 改為 A 方向單行，以及反向 B 方向單行：分開跑，不假設任何方向一定較好。
5. 只禁止特定轉彎：用於判斷改善是否其實來自路口衝突減少，而非整段封閉。
6. 對上述方案各自比較保留原號誌與重新調整號誌，清楚分開兩種效果。
7. 在需求範圍、不同起訖估計、遵從率與不同隨機種子下重跑。晴雨容量應依觀測校正；任意容量 −20% 只叫壓力測試。

建議以 SUMO 搭配迭代動態路徑選擇；確認迭代收斂，不只選最後一輪看起來好的結果。先建立現況基準，再做政策搜尋；不先用最佳化演算法挑一個「漂亮答案」。

## 怎麼判斷改善？

- **全區的人：**總旅行人時、中位數與最慢一成、各運具及不同起訖群體。不能只看全區平均掩蓋個別群體大幅惡化。
- **公共運輸：**公車旅行與等候、滿載未上車、接駁距離、駕駛休息與折返空間。
- **道路外溢：**鄰近路口排隊、研究邊界進出、車公里、回堵是否超過儲車長度。
- **可達性：**住戶、送貨、無障礙、救護、消防與公車是否仍可通行；無法抵達及未完成旅次都列出。
- **穩定性：**不同日子、季節、天氣、需求、隨機種子下的結果範圍。先訂精度與可接受誤差，再決定重複次數，不把任意次數當作統計保證。

一年資料能補足季節與晴雨代表性，不能自動證明因果。試辦應保留相似未試辦道路作對照並排除事故、工程與假日影響。GitHub 放小型摘要、索引與版本；完整年度原始資料改存物件儲存／Parquet，尚未建置該年度資料庫。
