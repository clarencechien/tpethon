# E14：已經分散的通勤，再錯峰能回答什麼？

[實驗Q&A](https://clarencechien.github.io/tpethon/experiments.html) · [互動細節](https://clarencechien.github.io/tpethon/staggered.html)

本輪不是重啟E13已停止的接駁班表調參，而是回到需求時間分布。**以已有多時段旅次作基準，只計新增實際移動，不能把原本已彈性的員工再算成政策成果。**

## 問題與答案

|問題|本輪能回答|尚不能回答|
|現在是不是已經分時？|旅次不是全部同時發生，晨間捷運有清楚的分時分布|企業採行率、可用彈性與員工實際使用率|
|再移出尖峰一小時會怎樣？|在指定比例下，分時人次會如何改變，是否形成另一個最高時段|列車擁擠、門到門時間、開車人數與道路減塞率|
|晚間分散會不會只是換時間排隊？|在固定容量的點排隊假設下，可能降低、維持或增加等待|成功路入口真實政策效果、其他道路改道與企業配合程度|

## 現況證據及「已經彈性」的界線

1. `data/simulation/service-inputs.json` 保存2026年9月22個週一至週五的捷運時段人次，未排除假日。研究對象為07–10時在來源站進站、目的地為西湖／港墘的旅次。不是07–10時抵達公司，也不代表全部內湖員工。
2. 三個進站小時的日平均分別為3,805.00、9,790.68、5,242.45人次，合計18,838.14，約20.2%、52.0%、27.8%。分散可能來自不同上班制度、旅程長短或其他旅次；不能由此識別彈性制度的因果效果。
3. 本輪重讀已保存的2012年《臺北市科技軸帶交通發展計畫（第一期）》PDF第77頁／正文2-17、第278頁／正文6-3，確實提到推動彈性上下班。這是規劃建議，沒有當作2026年企業採行率或政策後評估。來源與原檔校驗碼沿用[在地研究來源清單](../data/simulation/hub-local-research.json)；[官方資料頁](https://data.taipei/dataset/detail?id=25986a31-7e9f-45b2-8347-d047092295f5)。
4. 本輪未取得新的企業工時或實際出發調查。使用者提出「目前可能已經彈性」是應納入的現況考量，不直接替它填一個未驗證比例。

## A：晨間捷運分時人次的增量算術

以每個日期原始小時人次 `(h7,h8,h9)` 為基準，不重新造一個集中上班的反事實。

- 額外實際移動比例 `p = 0,5%,10%,20%`，**分母是原08–09時的旅次**，不是全體公司或三小時總人次。
- 提早比例 `a = 0`（全延後）或`0.5`（一半提早、一半延後）。移動幅度固定一小時；原資料只有小時解析度，不能假裝知道30分鐘移動的結果。
- `m = p × h8`；調整後為 `(h7+a×m, h8−m, h9+(1−a)×m)`。總人次完全守恆，既有07與09時旅次保持不變。
- 最高小時人次以三個時段重新取最大值，不一律把08時的下降當成新尖峰下降。
- 這是有條件的人次重分配，不是運具選擇、列車容量或壅塞模型；沒有「少了多少車」的輸出。

平均日10%再移動、一半提早一半延後：

|進站時段|實際平均|假設調整後|
|---|---:|---:|
|07–08|3,805.0|4,294.5|
|08–09|9,790.7|8,811.6|
|09–10|5,242.5|5,732.0|

約979人次移動，僅占三小時合計5.2%；最高小時人次下降10%。這個10%是算術情境結果，**不是政策已造成10%減塞**。人次小數是平均及期望值，不是切分實際乘客。

各日期獨立套用，保留低人次與假日。沒有把全月平均叫正常工作日，也沒有聲稱跨日算術穩定性等同實際政策驗證。

## B：晚間指定時窗的增量排隊機制

來源與[E3](SERVICE_EXPERIMENTS.md)相同：成功路南向入口，2026-10-15 16:30–20:30共241個觀測時點完整；末端20:30只是邊界，不多算一分鐘，使用240分鐘相對Volume權重。10/14只有239／241個有效值，完全停用該日，不補零。

VD測到已通過流量；塞住時它不等於上游真正到達量。原始統計區間尚未確認，所以只借相對型態，**3,000輛總需求與600／750／900輛每小時容量皆是假設**。不是從VD校正出來的真實車數或道路容量。

七種規則在三種容量下共21個條件結果：

1. 保留原型態。
2. 只允許彈性但實際時段不變，作零行為反應的對照。
3. 整批延後60分鐘，檢查只平移而不分散的反例。
4. 固定17:30–18:30時窗的10%延後60分鐘。
5. 同時窗10%的一半提早60、一半延後60分鐘。
6. 同時窗20%的一半提早60、一半延後60分鐘。
7. 同時窗10%的一半提早30、一半延後30分鐘。

指定時窗固定，不依每個結果重新挑最好看的尖峰。有效移動占17:30–18:30需求的比例，不是全日比例。3,000車假設下，10%時窗移動約80.7車，只占全批2.7%。移動者的替代時段均保留，不刪車或換算成減少旅次。

計畫窗延至21:30以容納全批延後，所有方案再清空120分鐘至23:30，使用同一長度。每分鐘以既有`queueStep`解析積分排隊；所有方案起始排隊0、容量固定、無其他時段背景車流、無空間回堵與改道。未清空則保留餘車及「累計等待下限」，不能拿較短的累計值當改善。

|容量假設|原型態車時|時窗10%延後60分|時窗10%分向前後60分|
|---|---:|---:|---:|
|600輛／小時|2,108.94|2,028.21|2,108.94|
|750輛／小時|608.94|528.21|608.94|
|900輛／小時|45.57|35.83|58.64|

750容量下，雙向分散可降低最高隊列261.6→237.8輛，但總排隊不減；900容量下，反而把一部分假設車潮移到較差時段，使總排隊45.57→58.64車時。**「最高隊列較短」「總等待較少」「每個人都更好」是不同判斷。**

整批延後60分鐘，在固定容量、無其他背景需求、相同初始排隊的模型內，只平移隊列而不減總等待；不能外推為真實道路所有平移都無效。現實容量、背景流與員工時程成本會改變答案。

移動時程負擔以`shiftPersonHours`或`shiftVehicleHours`保留，表示改變時刻的絕對幅度，不是損失時間或金錢，不與排隊時間直接相加。沒有假設人人願意配合、沒有估日程偏好或育兒成本，故不發布總福利或最佳政策。

## 如何驗證現況之上的額外效果

建議先收4–8週基準與對照資料，記錄既有彈性制度、實際使用、核心工時、會議、出發／到達、運具與接送限制。保持原制度，不把「沒有彈性」當現在的反事實。

依企業／部門分組，若可行採隨機分階段導入，增加一項可執行改變；否則以相近對照組做差異中的差異並檢查前趨勢。記錄實際移動，但主要效果仍依原分組報告，不只挑配合者。整個走廊有外溢，對照組也可能受影響，需一併觀測與揭露。

主要指標：原尖峰及新時段的實測旅行時間、P50／P95、總延誤與新增延誤、準時及營運KPI。控制星期、雨量、假日、事故、施工、學校作息。不能只以08時段流量下降判定整體改善，亦不能把進站人次下降叫車流下降。

這是研究設計建議，沒有已執行企業試驗或政策因果成效。既有方法脈絡及文獻查核狀態見[內湖研究盤點](research/NEIHU_RESEARCH.md)；本輪沒有把尚未讀全文的錯峰論文係數套進模型。
