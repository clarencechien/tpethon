# E12：有限車隊的班表搜尋與延誤驗證

[互動頁](https://clarencechien.github.io/tpethon/service-search.html) · [E11資料與模型](RAIL_HUB_TRIAL.md) · [E10道路代價](CORRIDOR_TRIAL.md)

本輪回答：**同一批既有鐵路轉乘旅客，混流接駁能否用較低費用，保留BRT行駛條件的一部分省時？挑好的班表遇延誤是否仍成立？**

不請求TDX或其他資料API。只讀版本控制中的E11輸入，重用原模型，不修改E11結果。沒有新的真實旅客、車程或班表觀測。

## 先看結論

240名合成既有鐵路旅客、列車間隔10分鐘、保留至少50%省時的組別：

- 在20個候選中，選到4輛營運車＋1輛備車、5分鐘銜接緩衝；原方式是2輛＋1備車。
- 挑選階段3個種子平均每人省12.18分鐘，BRT比較條件省22.55分鐘。候選不是在實際藍7或內科8班表上取得的效果。
- 候選每晨新增約6,690元，BRT條件新增約18,690元。**兩者約12,000元差額主要來自假設的BRT設施分攤；剔除該項後，本例營運費幾乎相同。** 不代表取得報價，也不證明較少車可以取代BRT。
- 鎖定設定後，另外3個種子 × 4種延誤共12次驗證，只4次同時通過所有門檻。未延誤3次全通過，列車＋步行延誤0次、巴士車程增加25%通過1次、全部延誤0次。
- 最嚴重驗證中，比同樣遭遇延誤的原方式多59人晚到。平均省時可以增加，卻仍使部分人由準時變晚到。
- 本組找不到同時保留80%省時、費用更低、無新增晚到且全完成的候選；這是20種設定的有限搜尋，不是對所有班表的不可行證明。

因此可以挑出需要實測的候選，也能指出延誤是風險，但**不能回答BRT無效、內湖實際少塞多少、真實公車應採哪一個時刻**。

## 使用的既有證據

- `data/simulation/rail-hub-inputs.json`：沿用已保存OSRM候選去返程與基地距離。路由是小客車候選路徑，非核准公車路線。
- E11另有官方方向別VD快照、四條既有公車站序與來源時間，可指出優先現勘位置與應比較的服務；**沒有把快照速度當整段巴士速度或容量，也沒把站序當班表**。
- 捷運松山→西湖／港墘人次沒有當作臺鐵下車數、合成旅客分布或新轉乘名額。
- BRT背景研究見[既有引用及原文頁碼](BRT_TRANSITION.md)。本輪是專案自訂情境枚舉與未參與挑選的樣本驗證，不使用文獻的減塞係數，也沒有聲稱統計顯著或因果識別。
- 使用者告知TDX用量已滿；停止新增API查詢。E11保留當時實際授權錯誤作為擷取紀錄，不將它解釋成資料不存在。

## 同一比較基準

每組條件固定合成人數120／240／480、列車到站間隔6／10／15分鐘，共9組。

- 原方式：2輛營運車、首班07:00、目標10分鐘班距。計畫與實際班距均受往返週期及車隊限制。
- 混流候選：2／3／4／5／6輛 × 銜接緩衝0／2／5／8分鐘，共20種。首班07:00＋步行6分鐘＋緩衝；目標班距與列車間隔相同。
- BRT比較條件：固定4輛、緩衝2分鐘、目標班距與列車相同；採E11較短行駛、停站與號誌時間假設。不是經搜尋最佳化的BRT，結論不表示兩類服務的最佳可能性能。
- 比較中原方式與BRT規格都不隨候選變動。每個種子使用相同旅客ID、列車批次、出門時間與到達期限。
- 只含既有鐵路旅客，原開車者設0；沒有任何減車結果，也沒有停車補助或新增鐵路名額假設。
- 每車60人，休息12分鐘，備車為10%向上取整；本輪車隊範圍皆為1輛備車。原方式也計備車。
- 原假設出門至松山30分鐘、到站牌6分鐘、到辦公室5分鐘，到達期限為出門後75分鐘；列車到站涵蓋07–09時、巴士發車至10時、觀察至12時。不是實際上班時刻。

完整派車、取消空班、車輛返回、延誤與費用計算沿用[不變的E11模型](../static/rail_hub_logic.js)。本輪並未新增路口、道路容量或行為選擇模型。

## 挑選與驗證分開

### 挑選

使用固定種子7、19、41，均無額外延誤。9組 × 20候選 × 3種子＝540次候選評估。

對50%與80%兩種省時目標，候選必須在**每一個挑選種子**都符合：

1. 相對原方式每人平均至少省3分鐘，且至少達到該種子BRT省時 × 目標比例；BRT省時需為正。
2. 沒有新增晚到，且所有人12時前完成。
3. 相對原方式新增費用嚴格低於BRT條件。

平均省時以配對旅客的完成時間差計算；未完成以12時截尾計算差值並另外計人數，不藉排除未完成者美化平均。候選有未完成則不得通過。

合格者取3種子的平均新增費用最低者，再依車數少、緩衝短破同分。沒有合格者保留null，不偷偷放寬門檻。

### 驗證

鎖定所選車數與緩衝，使用未參與挑選的101、211、307三個種子，測試：

|條件|列車晚到|額外步行|巴士去返程倍率|
|---|---:|---:|---:|
|無額外延誤|0|0|1|
|轉乘延誤|5分|3分|1|
|道路延誤|0|0|1.25|
|兩者同時|5分|3分|1.25|

每個選中的方案有12次驗證；班表規劃看不到實際延誤。原方式、候選及BRT都遭遇相同延誤，新增晚到逐人對照原方式。同一方案若同時被50%與80%目標選中，驗證旅次是相同的，只有達標門檻不同，不能當獨立樣本。

驗證不重新選車數或緩衝。9組中50%目標皆找到候選，80%目標4組找到，合計13份目標驗證、156筆結果（包含重複方案）。沒有一份通過其全部12次驗證。

有限人數與種子不是真實需求抽樣；所有旅客仍使用同一合成到站分布，延誤是同時套用的常數。換種子只驗證這個合成生成器，不能代替獨立實際日期或一般化到全年。達標次數不是可靠度機率。

## 成本與效益邊界

沿用每車小時1,200元、保留車隊及備車至少3小時、超時返回另計。BRT每晨設施分攤12,000元是假設，會影響哪個方案被視為較便宜。頁面另外列出扣除該項後的營運費差；本輪沒有重新搜尋其他分攤值下的候選，不能把同一選擇外推到不同報價。

費用未納入真實場地租約、工程設計、號誌優先設備等報價。各方案的速度與訊號時間尚未實測校正，BRT也未計一般車道減少的代價。不得把這裡的旅客省時當成道路減塞率、每人社會效益或工程投資報酬。

## 下一輪如何補強

先用實際站內步行、列車到站、公車去返程重播挑出的設定，再決定是改動線、保留銜接緩衝、加車或測試號誌優先。可研究有上限的等候接車策略，但必須同時計入車上旅客延誤、回程及休息、後續班次連鎖影響，不能只讓轉乘者受益。

在取得真實資料前，能排除明顯不穩定的設定、安排量測優先順序；尚不能據此調整真實公車服務或實施道路管制。

```sh
node scripts/run_service_search.mjs
node --test tests/service_search_logic.test.mjs
```

輸出 `data/simulation/service-search-results.json` 包含全部540次挑選結果、選定候選、未參與挑選的驗證、輸入／E11模型／E12搜尋邏輯／執行器SHA256。產物沒有新的擷取時間，避免把重算日期誤認成觀測日期。無金鑰、無網路、無額外套件需求。

瀏覽器測試 `python tests/service_search_pages_smoke.py` 使用本機8001埠網站，驗證條件切換、未找到方案的狀態、完整下載、手機閱讀與缺檔處理。
